# V12 · 聊天前端优化设计

> 站点: `chat.luxera.top`(仓 `chat-platform`,前端 `frontend/`)
> 姊妹文档: `../../simulation-agent-platform/docs/V12-console-frontend-design.md`
>
> 这两个前端是**同一个产品的两个站点**, 但它们对**两拨不同的人**说话。这份文档只写
> 这一半 —— 一个用户在自己的聊天软件里, 怎么看见"对面是一个在过日子的人"。

---

## 0 分工: 这一半不画什么

先说不画什么, 因为这一半最容易被"顺手也做一份"污染。

| 问题 | 在哪个站点回答 |
| --- | --- |
| 她今天在做什么? 计划表怎么改了? 她跟这个人熟不熟? 她手机响不响? | **`being.luxera.top`**(控制台) |
| 我跟她说了什么? 她回了我什么? 我要不要被这一段打扰? | **`chat.luxera.top`**(这一站) |

判据是**主语**:

- 主语是**她**的("她的计划"、"她的关系"、"她的手机") → 控制台
- 主语是**我**的("我的消息"、"我不想被打扰"、"我的账号ID") → 这一站

一条推论: 这一站**不提供**任何"看她的内心"的页面。曾经有过 —— 老实现里
`Chat.tsx` 有 7 个抽屉, 记忆/用户模型/关系/最近都在聊天室里。它们被搬到了
`contacts/agent/:companionId` 资料页与控制台, 因为一屏"我在跟她说话"里塞进
"她的 intimacy 字段是 0.42", 会把聊天室变成一块仪表盘。

## 1 现状盘点

| 项 | 现状 |
| --- | --- |
| 规模 | `src/` 下 128 个文件, 约 **17 118 行** TS/TSX |
| 路由 | `routes.tsx`: `tabRoutes`(4 tab) + `fullScreenRoutes`(全屏, 无 tab bar) |
| 实时 | **SSE**, `useConversationEvents` + `api/client.ts` 的 `openEventStream` |
| 样式 | Tailwind 3.4, 语义 token, 与仓 2 **逐字相同** |
| 测试 | 37 个测试文件 / 463 条, `renderToStaticMarkup` 可用(组件结构可断言) |

### 1.1 四个具体问题

**Q1 · 免打扰开关有实现、零调用点。**
`src/api/conversations.ts` 里 `setMuted` 与 `setPinned` 写完了, 而 `src/` 下**没有
任何一处调用它们**。这意味着产品原话里最硬的那一条:

> 每一条消息都会根据用户在聊天软件里设置的通知规则(DND)来决定要不要通知她

在界面上是**不可表达的**。用户没法设免打扰 —— 于是"她怎么不回我"永远不会有一个
诚实的答案, 而正确答案可能是"你上周自己把它静音了, 然后忘了"。

**Q2 · "我把它设成免打扰了"没有痕迹。**
即使补上开关, 那个开关只在**打开那一段对话**时才看得见。而人不会没事去点开一段
他没在等的对话。**忘记才是这个功能真正的故障形态** —— 故障发生在用户奇怪"她怎么
一直不回我"的那一刻, 而那一刻他的屏幕上什么都没有。

**Q3 · 聊天室页头副标题是一句恒定的类型说明**("仿真 Agent"), 占着页头最贵的一行。

**Q4 · 会话列表里没有任何地方能看出"我把这一段静音了"。**

### 1.2 不是问题、是被确认的对的东西

- `routes.test.ts` 用 `renderToStaticMarkup` 做结构断言这条路是通的 —— 仓 2 没有
  jsdom, 这里能测 JSX 结构, 所以这一站的界面约束可以钉得更死。
- `openEventStream` 的重连退避(1s → 30s)与 `Last-Event-ID` 游标续传已经在了。

## 2 信息架构

### 2.1 这一站也有两拨人, 但第二拨不是"运维"

控制台那两拨是**看她的人**与**运维/开发**。这一站的两拨是:

| 拨 | 是谁 | 在哪 |
| --- | --- | --- |
| 主 | **用户自己** —— 在跟一个仿真的人聊天 | 四个 tab + 各全屏页 |
| 次 | **第三方应用** —— 跑在 `SurfaceHost` 里的宿主页 | `/applications/:id`、`/sessions/:sessionId`、`/join/:token` |

第二拨不"看"这个应用, 它**住在**这个应用里。所以它与第一拨的隔离不是分工, 是
**边界**:

- 宿主页(`ApplicationFrame`)拿不到用户的聊天数据, 只拿到 `bridge` 明确暴露的能力
- `/applications/**` 与 `/sessions/:sessionId` 是**全屏**的, 进去之后没有 tab bar —— 
  一个第三方应用里压着一条聊天应用的 tab bar, 会让人分不清"哪个是应用、哪个是壳"
- `/api/**` 是后端独占前缀, SPA 路径不许落在它下面: 一个挂在它下面的页面只在客户端
  跳转时正常, 直接访问或刷新时浏览器发的是 document 请求, 被 nginx 交给后端, 页面
  代码一行都没跑

### 2.2 四个 tab 与它们各自回答的问题

```
/chat        我的消息 —— 谁找过我、我说到哪了
/contacts    我的联系人 —— 有谁是"活人", 我跟他聊过什么
/discover    我能玩什么 —— 应用平台能给她做什么
/me          我自己 —— 提醒、通知、免打扰、账号ID、外观
```

四栏是**微信的形状**, 这个形状不是抄来的, 是它在这个场景上确实最省:

- 打开就是消息列表, 没有"首页"这个概念(`/` 重定向到 `/chat`)
- `/chat` 是**精确匹配**的 tab 高亮 —— 否则进聊天室时它会错误地继续亮着
- 全屏页(`/chat/:conversationId`、`/contacts/**`、`/me/**`)挂在与 tab 分支**同级**的
  另一条 `RequireAuth` 分支里, 而不是嵌套在它下面 —— react-router 7 里要让一组路由
  换掉父级外壳, 这是唯一干净的做法

### 2.3 `chat/:conversationId` 下面不许有静态子路由

一条硬约定, 写在 `routes.tsx` 的注释里并由 `routes.test.ts` 钉住:

```
{ path: '/chat/:conversationId', element: <ChatRoom /> }   // ← 它下面不许再挂
```

一旦有人加 `/chat/new`, react-router 会把 `new` 当成会话 id 匹配进来 —— 症状是
"点发起群聊进入了某个人的聊天室, 而且那一段 id 是 `new`"。**"发起群聊"这类入口用
弹层, 不用路由。**

`/contacts/**` 那三条**没有**这条约束: `:companionId` 是真的一个人, 而
`new` / `settings` 被路由表静态匹配掉, 走不到参数里去。

### 2.4 会话由 `conversationId` 寻址, 不是 `companionId`

老实现里会话是组件 state, 于是刷新页面会跳到"第一个会话"而不是你在看的那个 ——
因为 URL 上只有伴侣 id, 而**一个伴侣可以有多段对话**。现在点进来、刷新、分享链接、
按后退都落在同一段对话上。

## 3 通知与免打扰 —— 这一站最重要的一节

### 3.1 免打扰不是"小声一点"

这是整个产品里**最容易做错的一处**。把「免打扰」实现成"信号照样发出去, 只是音量调低"
是很自然的下一步。那样做之后有一个具体的坏结果:

> 用户以为自己屏蔽了, 而她的手机照样会响, 然后在某一天被"我不是设了免打扰吗"问住。

正确的语义只有一个: **平台根本不发那条通知信号。** 她那边什么都不会收到 —— 连"隐约
感到"都没有, 因为她压根没被通知过。她想起来去看手机的时候才会看到。

这条语义写在**用户点开关时正对着的那一行字上**(`lib/notificationSettings.ts` 的
`SWITCH_COPY`), 不只是写在文档里。因为这句话一旦只存在于文档, 它会被实现悄悄地
破坏 —— 只要有人在通知的载荷里塞一个发信人就够了, 而**没有任何编译期错误、没有任何
接口变化、没有任何前端代码需要改**。

`notificationSettings.test.ts` 因此对**文案内容**做断言(23 条), 而不是只断言"返回了
一个非空字符串"。这类断言通常被嫌脆, 但脆在这里正是要的东西。

### 3.2 置顶更危险, 因为它看起来像免打扰的邻居

「置顶聊天」只影响**你自己**那张列表的顺序, 她那边一个字都不变。
一个把置顶读成"优先找她"的用户会以为自己提高了这条消息的优先级 —— 而它只是一个
排序字段。所以它旁边的说明必须明写"**只对你有效**", 且不能和免打扰共用一个"通知"
类的标签。

### 3.3 两个开关住在两个地方, 是同一份数据

| 位置 | 回答什么 | 为什么需要 |
| --- | --- | --- |
| 聊天室页头的铃铛 | "**这一段**我现在不想被打扰" | 决定发生的那一瞬间, 你在这一段对话里 |
| 「我」→ 会话免打扰 | "**我把谁**静音了" | 决定需要被回想起来时, 你不在任何一段对话里 |

第二处不是"设置该有个汇总", 它是 Q2 那个故障形态的唯一解药: 一页能一眼扫完的列表,
是"我上周把它设成免打扰了"这件事唯一的线索。

两处**共享同一份数据**, 不是两处设置。聊天室那个面板改完之后写回 store, 页头副标题
立刻跟着变 —— 不需要刷新。

### 3.4 乐观更新 + 失败回滚

这两个动作**只影响用户自己眼前这一屏**, 所以让它等一个网络往返是把本地事实加上了
延迟。而乐观更新的正确性全在回滚那一步:

> 不滚的表现是"开关看着是开的, 而服务端上是关的" —— 一个用户没有任何办法发现的撒谎。

所以 `catch` 里那两行不是防御性编程, 是正事。失败时还会显式说一句"开关已经拨回去了
—— 服务端上还是原来的样子"。

### 3.5 免打扰是两层, 页面上摆两层

| 层 | 住在哪 | 决定什么 |
| --- | --- | --- |
| 第一层 | **聊天平台**(`ConversationNotificationSetting.muted`) | 要不要**发出**那条通知信号 |
| 第二层 | **她的手机**(`NotificationPolicy`: 通知/铃声/闹钟/媒体四通道 + 它自己的 DND) | 信号到了之后**怎么响** |

两层都不是对方能替代的。还有第三种"她没反应": 她**自己在做什么**(睡着了、专注在一件
事上) —— 前两种是设置, 第三种是状态。**三种原因完全不同, 所以不能当成同一件事去调。**

### 3.6 通知一条一条, 从不聚合

产品原话: 那些要通知她的消息**一条一条**地通知, 像微信/QQ, 从不合并成"3 条新消息"。

这一站是**用户侧**的读面, 所以这里可以聚合(会话列表本来就该显示"3 条未读")。
克制的是**不要把这个习惯带到她的那一侧** —— 她的通知通路上没有任何"合并"的逻辑,
也不该有。

## 4 消息正文只在"她自己去看"那条路上

### 4.1 规则

> 她收到的通知**不带消息正文**。只有当她**自己做出"看一眼手机"这个动作**时, 才去调
> 聊天平台的接口拉会话列表与聊天记录。

这条规则管的是**她那一侧**, 也就是仓 2 的控制台。这一站是用户自己的聊天软件, 用户
当然能看见自己发的消息。两件事互不冲突。

但它在这一站留下一个可检查的约束, 因为最容易破坏这条规则的地方恰好在这里:

**不许有任何"推送 / 预览 / 通知栏"类的前端功能去替她省掉那个动作。** 具体地说,
这一站不提供:

- 浏览器 Web Notification 的"她的消息来了"弹窗(我这边收到就行, 不需要替她感知)
- 把消息正文塞进任何一条**给她**的载荷里

### 4.2 她的通讯录是她自己长出来的

产品原话: 她的通讯录是通过聊天**自己长出来的**, 不是从平台同步的。

这一站是**平台侧**。所以「通讯录」这一栏列的是**我**的 Agent 名单(`agent_...`) ——
不是她的通讯录。两者容易混, 因为两边都叫"联系人", 都画头像。

界面上不提供"给她加一个联系人"的入口。那个入口一旦存在, 她的通讯录就变成平台
同步的了。

### 4.3 关系类内容搬去了资料页

聊天室里曾经有 7 个抽屉(记忆 / 用户模型 / 关系 / 最近 / 提醒 / 通知 / 应用)。现在:

| 原来在聊天室的抽屉 | 现在在哪 | 为什么 |
| --- | --- | --- |
| 应用 | 聊天室「+」面板 | 它是"我们做点什么", 属于这一段对话 |
| 记忆 / 用户模型 / 关系 / 最近 | 联系人资料页 | 主语是**她**; 聊天室是用来聊天的 |
| 提醒 / 通知 | 「我」 | 主语是**我**, 而且它们恰恰是"我不在聊天室里"时才需要知道的 |

## 5 交互与视觉规范

### 5.1 与仓 2 共用同一份 token(逐字相同)

两个前端的 `tailwind.config.js` 与 `src/index.css` 的 `colors` / `:root` / `.dark`
**逐字相同**。不是"抄一份保持一致", 是同一个定义写了两处 —— 两个前端属于同一个产品,
而"同步"这件事只要靠人去记, 就一定会漂; 漂的表现是某个按钮在两个站点里是两种蓝,
那种错误没人会报告, 但所有人都会觉得哪里不对。

**核心决策: 语义 CSS 变量 + `darkMode: 'class'`, 组件只用语义名, 全项目零 `dark:` 前缀。**
于是双主题的成本是每个概念**一个类名**, 而不是每个类名两遍。

| 概念 | token |
| --- | --- |
| 面 | `surface` / `raised` / `sunken` / `scrim` |
| 线 | `line` / `line-strong` |
| 字 | `ink` / `ink-soft` / `ink-faint` |
| 强调 | `accent` `#2563EB` / `accent-soft` / `accent-ink` |
| 语义 | `ok` / `warn` / `danger` |
| 气泡 | `bubble-in` / `bubble-out` / `bubble-out-ink` |

亮色是默认(产品决定: 没选过主题的用户、以及任何读不到 localStorage 的场景都该落到
亮色)。`<html class="dark">` 由 `index.html` 里一段内联脚本在**首屏渲染前**写上 ——
放 React 里会在首屏后闪一下白。

### 5.2 尺寸与间距

- 正文 `text-sm`; 时间戳与状态 `text-[11px]`
- 触摸目标不小于 36×36(页头按钮是 `h-9 w-9`), 会话行整行可点
- 消息流 `max-w-2xl` 居中; 页面 `px-3` 起, `sm:` 起 `px-6`
- 圆角: 控件 `rounded-lg`, 卡片 `rounded-xl`, 气泡用气泡自己的形状

### 5.3 消息流的两条姿态

1. **消息贴着输入框往上长**, 不从顶部往下堆 —— 新的消息出现在**离拇指最近**的地方,
   而一段刚开始的对话不该顶在屏幕最上方、下面留一大片空白。
   用 `min-h-full` + `justify-end`, **不是**把 `justify-end` 加在滚动容器上 ——
   后者在内容超过一屏时会把最上面几条裁掉, 而且滚不回去(flex 的经典坑)。
2. **不锁输入框。** 老实现的 `inputLocked = streaming && !gathering` 意思是"等她说完
   你再说", 那是 AI 伴侣的语汇。真人聊天时对方打字完全不妨碍你继续发。

### 5.4 空 / 加载 / 错误

| 状态 | 这一站的做法 |
| --- | --- |
| 空 | `EmptyState` 说清"还没有消息, 说点什么吧", 不给一个假的示例气泡 |
| 加载 | 一行"加载中…"; 不整屏骨架 —— 聊天室的加载是"这段对话的消息到了没有" |
| 错误 | 就地一条红色横条 + "知道了", 不做全屏错误页 |

### 5.5 开关的视觉

`Switch` 是 `<button role="switch" aria-checked>`, 轨道**两边不同色**: 关着画成
`sunken`(凹), 开着画成 `accent`。只用滑块位置区分开关状态在小尺寸上看不出来 ——
而"我到底开没开"就是这一屏的全部信息。

滑块与行程都是**算出来的**任意值: 轨道 44×24, 滑块 18×18, 行程 `44 - 18 - 2 = 24px`。
写成 `h-4` 或 `h-5` 会让滑块要么四周漏光要么顶到轨道边, 而漏光那种错在小尺寸上看起来
只是"有点歪", 没人会去查。

### 5.6 文案

- 一律中文; 技术标识(端点、状态码)不翻译
- **开关的说明写"不设它会发生什么", 不写"已关闭"** —— 一个只写"已关闭"的开关没有
  告诉任何人默认行为是什么, 而默认行为恰好是这个开关唯一需要被理解的另一半

## 6 无障碍

### 6.1 键盘

- 每个可点元素都是 `<button>` 或 `<a>`, 没有 `onClick` 挂在 `<div>` 上
- `ListRow` **有 `onClick` 时渲染成 `<button>`, 没有时渲染成 `<div>`** —— 这条不是
  洁癖: 带开关的行如果是一个大 `<button>`, 里面的开关要么点不动, 要么点开关的同时
  把整行也点了一遍(`<button>` 里不能嵌套 `<button>`)。「我」→ 会话免打扰那一页正是
  这种情况, 所以那里每一行都不给 `onClick`
- 弹层可 `Esc` 关闭

### 6.2 读屏

- 开关报的是 `role="switch"` 的"开/关", 不是 checkbox 的"已勾选/未勾选" —— 这两个
  开关切换的是**一件一直在生效的事**, "开"才是它真正的语汇
- 开关旁边那行字是**视觉**标签, `aria-label` 才是读屏听到的(要说清"**哪一段对话**的")
- 聊天室页头被划掉的那个铃铛是**装饰**: 那道斜线 `aria-hidden="true"`, 语义由副标题
  的文字("免打扰 · 置顶")承担 —— 一个只靠图标变灰表达的"她被静音了"对读屏是不存在的
- 未读数在 `aria-label` 里读成"3 条未读", 而不是读成一个孤零零的数字

### 6.3 对比度与不靠颜色

- 正文对比度 ≥ 7:1(`ink` 在 `surface` 上)
- `danger` 的红横条同时带一行文字, 不是只有颜色
- 免打扰的会话行**同时**有一个副标题文字, 不是只把标题变灰

## 7 性能预算

### 7.1 首屏

| 指标 | 预算 | 现状 |
| --- | --- | --- |
| 主包 (gzip) | ≤ 200 kB | 127 kB |
| CSS (gzip) | ≤ 12 kB | 6.7 kB |
| 首屏可交互 | ≤ 1.5 s (4G, 中端机) | 待实测 |

**没有路由级代码分割** —— 理由与控制台那条一样: 包已经比一张图片小。预算的作用是
未来: 超过 250 kB 时再讨论。

### 7.2 实时: SSE, 而且是手写的 `fetch` 流

这一站的实时通路是 **SSE**, 但用的是 `fetch` + `ReadableStream`, **不是**
`EventSource`。理由只有一条, 但它是硬理由:

> `EventSource` **不能带 `Authorization` 头**。

这一站的认证是 Bearer token(不是 cookie), 用 `EventSource` 就只能把票塞进 URL 的
query —— 那会让票出现在服务端日志、浏览器历史、以及任何 `Referer` 里。

自己解析 SSE 帧的代价是几十行(`\n\n` 分块 + `TextDecoder`), 换到的是:

- **`Last-Event-ID` 游标续传**: 断线重连时带上上次收到的事件 id, 服务端从那儿续
- **指数退避** 1s → 30s, 连上即重置
- **`AbortController`** 精确关闭, 不依赖 `EventSource.close()` 的语义

### 7.3 一条连接, 不是每切一次会话一条

`useConversationEvents` 的依赖数组里**只有 `peerId`**。

老实现把"连接"与"这条事件是什么意思"写在同一个 `useEffect` 里, 依赖是
`[companionId, activeConvId]` —— 于是每切换一次会话就重开一条 SSE, 而事件处理器
在整个 effect 里重建, 于是"这条事件属于哪段会话"只能在闭包里判, 而闭包里的
`activeConvIdRef` 是异步更新的。

分开之后: 连接只在伴侣变化时重建(这是对的 —— 事件流本来就是按伴侣开的), 而"这条
事件是什么意思"由调用方在**每次渲染时的最新闭包**里判。`onEvent` 走 ref, 于是处理器
永远是最新的那一版, 连接始终只有一条。

### 7.4 轮询的公共规矩

- 页面不可见时停止(`document.visibilityState`)
- 请求失败退避, 成功即恢复
- 同一端点在同一时刻至多一个在飞的请求

### 7.5 消息列表

一段对话的消息按"一屏几十条"量级。**不做虚拟化** —— 虚拟化在这个量级上带来的是
"滚动时气泡闪一下"这种真损失, 换来的是一个不存在的问题。真正的量级问题是"打开了
一段三年的对话", 那个该由**分页**解决, 不是由虚拟滚动解决。

## 8 后端缺口清单(这一站需要、服务端还没有)

同样: 这是**报告**, 不是待办。这一站的边界也是"不改后端 Java"。

| # | 缺什么 | 用在哪 | 现在的样子 |
| --- | --- | --- | --- |
| C1 | `GET /api/conversations` 的每一行带上 `muted` / `pinned` | §3.3 的两个开关 | **已经有了** —— 见下。而且比本条假设的更好: 不是"存下来的一列", 是**按请求时刻现算**的 |
| C2 | 设置免打扰/置顶后, **服务端回显**成新值 | 乐观更新的确认 | **已经有了** —— 见下 |
| C3 | 一个"这段对话被静音了"的**事件**, 供 SSE 广播 | 多端一致 | **仍然缺** —— 在 A 设备上设的免打扰, B 设备刷新前不知道 |
| C4 | `PUT /api/conversations/{id}/notification` 的**权限说明**: 这是平台侧设置, 不影响她的手机 | §3.1 的文案 | **已经是这样** —— 见下 |
| C5 | 通知载荷里**不含 `content`** 这一条要有一个可验证的约定 | §4.1 | **已经有了** —— 见下 |

**C1 / C2 / C4 是查过之后关掉的, 不是"看着像已经有"**。三处的证据:

- **C1** —— `contract/.../client/ClientConversation.java` 的记录分量里就有 `pinned` 与
  `muted`, 而 `ClientConversationService.list(...)` 每一行都从
  `ConversationReadState` 现算再填。两个开关因此**不可能是 `undefined`**。
  这里有一处刻意的选择值得记住: `muted` 用的是 `isMuted(s, now)` —— **此刻**的判定,
  而不是 `mutedUntil` 那一列本身。理由写在那一行旁边: 一个已经过去的 `mutedUntil`
  不该让这一行永远显示"免打扰中"。也就是说 `muted` 与 `pinned` 是**两种不同的东西**
  (`pinned` 是一个状态, `muted` 是一个判定), 它们只是恰好都长成一个布尔值。
- **C2** —— `ClientConversationService.setNotification(...)` 的返回值是
  `new ConversationNotificationSetting(conv.getId(), muted, pinned, state.getUpdatedAt())`,
  即**服务端回显**, 而不是一个空 ack。于是"成功但没改"这条歧义路径不存在:
  回显里那个值与请求里那个值不一致时, 前端就能看见。
- **C4** —— `ClientConversation.muted` 的 javadoc 第一句就是
  "**这是平台侧的那个开关**: 它为真时, 平台一条 `NotificationSignal` 都不发"。
  它与 §3.1 页面上那句文案是同一件事的两种说法。另外
  `ClientNotificationService` 的注释把判定的**时刻**也说死了: 免打扰是在**发通知的那一刻**
  读 `conversation_read_state.muted_until` 现判的, 而不是一个被传下来的布尔值 ——
  这条决定了"她手机响不响"的判定权始终在聊天平台这一侧, 与 V2.2 §6.2 的分工一致。

**C3 是这一节里唯一还开着的, 而它的性质要说清楚**: 它不是"少一个接口", 而是
**多端一致性的缺失** —— 免打扰的设置住在服务端, 但**变更本身没有事件**。
两台设备同时登录时, A 改了, B 要等下一次刷新列表才知道。修它的正确形状不是新加一个
轮询端点, 而是让设置变更走一条已有的广播通道(与 `NotificationSignal` 同一条长连接,
但**方向相反**: 那是服务端→客户端, 而这条是"客户端的另一个会话"→客户端)。
**它没有被修, 是因为它需要先回答一个设计问题**: 这条广播要不要带 `conversationId`?
带, 就等于把"谁被静音了"告诉了所有在线会话; 不带, 客户端只能整个刷新列表。
在那之前, 页面上按 §3.3 处理(乐观更新 + 失败回滚), 单设备体验是完整的。

**C5 是这一节里唯一真正重要的一条, 而它已经关掉了。** 整份设计的核心是"通知不带
正文" —— 而它在服务端是一个**减法的约定**(某个字段不填), 减法的约定没有编译期保护,
也没有测试能测"某个字段没有被用到"。所以它必须被写成一条会红的断言, 而不是一句
注释:

    chat/src/test/java/com/luxera/companion/client/NotificationSignalShapeTest.java

它断言的不是"这一次实现有没有写漏", 而是 `NotificationSignal` 的**分量集合本身** ——
任何人往信号上加字段(一个 `preview`、一个 `senderName`), 那条用例都会红, 而它红的
地方正是他需要停下来想一次的地方: 这一个字段是不是内容?

同一个类里还钉着一条反面对照: V10 那个 `PhoneNotificationPayload` 带着 `preview`
与 `privacyMode`, 也就是说它可以被调用方**打开成 FULL_PREVIEW**。§6.1 要的不是
"默认不预览", 而是"这个开关不该存在" —— 只要开着它是可能的, 某一个调用方就会把它
打开, 而服务端无从拒绝。所以那个类型**不许被接回来**当通知载荷用, 这条也写了测试。

**另有一条不是缺口、是约束(不许被重新引入)**: `/api/` 路径**不套 Authelia**
(三方机器客户端要 401 不要 302), 静态页套。浏览器的 XHR 如果被 302 到登录页, 会
表现成"登录了却连不上后端"。Service Worker 会缓存旧的 302 —— 遇到过就把 `sw.js`
404 掉、XHR 改返 401。
